# Plan — wysiwyg-grilling v0.9: failure paths, stale derivations, and the event loop said plainly

**Input:** assessment run 5 (`capability-assessment-notes-optimizer_R5.md`),
19 findings / 18 causes / 7 P1 / 0 P0, two arms, ledgers `.ledger/r5.jsonl`
and `.ledger/r5b.jsonl`. **Target branch:** `v0.9_failure_paths` off
`v0.8_correctness`. Nothing is merged to `main` yet and this plan does not
change that.

## The through-line

Run 4 said *capability outgrew correctness*. v0.8 fixed the surfaces the agent
reads. Run 5 found what sits underneath them, in two sentences:

1. **The write paths are atomic when they succeed and lossy when they fail.**
   A rejected batch still writes its registry ops; a restart destroys a queued
   revision; a cross-artifact pin resolve strands its glyph. All three are
   invisible unless somebody diffs the state afterwards. *(The agent under
   test named this shape itself, unprompted, after living through two of them.)*
2. **The standing channels report a world that no longer exists.** Referential
   errors frozen at server start; a round derived from queue depth that
   un-derives itself; a repair recomputed on every load and persisted on none;
   a guard that filters a field nothing writes.

Every P1 is one of those two. The work packages are cut along them, not along
severity.

## Definition of done (unchanged from v0.8, plus one addition)

Every fix needs a **differential control in both directions** — it fires on the
defect *and* stays quiet on the legitimate neighbour — plus **replay against
the promoted fixtures** (`tests/fixtures/argus-r4-arm3`, `argus-r4-arm4`,
`argus-r5`).

**New for v0.9, and it is the lesson of `r5-14`:** for anything whose
deliverable is a rendered image, the gate is a **rendered** check, not an
assertion over stored geometry. `r5-14`'s path was provably correct and the
picture was still broken. Where a defect is visual, the test renders and
measures pixels, or it does not count.

**And as of the Aug 2026 literature scan that rule has a mechanism** — see WP4's
*render verification* item. The short form: render twice, once with the element
under test hidden, and diff. An element whose ablation changes **no** pixels is
invisible; a connector whose ablation delta splits into **two** components is
visually severed. That second assertion is `r5-14` caught from pixels, with
certainty, and localised to the gap. No baseline images, no ML, no thresholds.

## WP1 — Failure-path atomicity and durability (r5-8, r5-18, r5-17) — ships alone, first

The only cluster that **destroys or corrupts user-directed work**. Three
mechanisms, one theme, one acceptance test.

### r5-8 — a rejected batch still writes its registry ops

`_validate_batch` mutates the live registry while validating (the `set_round`
branch does `errors.append(...)` in one arm and `reg["round"] = op["round"]` in
the other, on the same object). Measured: a batch rejected with two `ERROR=`
lines left `Zeta` on `/api/state` while the disk stayed clean; the next commit
persists it. Arm B traced the durable consequence — 25 `add_mapping` ops and 9
`remove_mapping` in the save records against 22 live mappings, which only
balances if six entered `model.json` with no save record.

**Fix:** validate against a deep copy; swap it in only when the whole batch
passes. The `--check` path already does this via `_sandbox()` (`canvas.py:7758`)
— the commit path (`:6815`) rolls back `artifact_meta` only. Make the commit
path use the same sandbox.

**Controls:** (a) a batch with one invalid and one valid registry op leaves the
server registry *and* disk byte-identical; (b) an all-valid batch still applies
every registry op. Plus a re-apply test: fix the invalid op, re-send the same
batch, assert `add_mapping` did not duplicate.

### r5-18 — a queued revision is destroyed by a restart, silently

Reproduced: `PENDING=1` → `stop` → `start` → `PENDING=0`, with no warning at
stop, no note at start, and no record anywhere. `stop` is the **documented**
way to end a session.

**Fix, in order of preference:**
1. **Persist the queue** to `project_knowledge/.pending/` and restore it on
   start. This is the honest fix — the queue holds agent-authored, user-awaited
   content and has no business being memory-only.
2. If (1) is judged too large: `stop` must refuse with
   `ERROR=N revision(s) waiting behind the banner — apply or discard first
   (canvas.py pending --discard <id>)`, and `start` must print
   `NOTE=N queued revision(s) were lost when the server stopped` by comparing a
   written-at-queue-time manifest against an empty queue.

**Controls:** queue → restart → the revision is still there (or, under (2),
`stop` refuses and `start` says what was lost); and an empty queue restarts
silently, with no spurious note.

### r5-17 — a cross-artifact `resolve_pin` strands its glyph

`resolve_pin` looks the ❓ up in the *batch artifact's* index; when the pin
lives elsewhere the tolerant branch fires, the registry resolves it, and the
glyph stays drawn forever. `status` said `OPEN_PINS=3` while four glyphs were
on the canvas. **SKILL.md instructs the shape that triggers it** — "the batch
that executes an answer also carries its mirrored pin's `resolve_pin`" plus
"one batch = one artifact".

**Fix:** resolve the pin's glyph in *its own* artifact regardless of batch
scope (the registry already knows which artifact each pin is on), and keep the
tolerant branch only for a genuinely already-deleted glyph — reporting it as
`NOTE=pin <id> resolved; its ❓ was already gone`.

**Controls:** resolve from a foreign batch → glyph gone, `OPEN_PINS` matches
the glyph count; resolve a pin whose glyph the user already deleted → resolves
quietly with the NOTE, no error.

**Why this matters more than its severity suggests:** arm A's agent hit `r5-17`
and **apologised for it as its own carelessness**. A tool whose silence
converts its bug into the agent's guilt corrupts every attribution downstream.

### Acceptance gate for WP1

One test module, `TestFailurePathAtomicity`, whose every case follows the same
shape: **cause a failure, then diff the state.** Not "assert the happy path
still works" — that is what shipped these three.

## WP2 — Stale derivations (r5-19, r5-2, r5-3, r5-13-adjacent)

Four surfaces that cache a value and never invalidate it. **This is also the
round-6 prediction both arms converged on**, so fixing it well is how run 6
gets a harder target.

### r5-19 — referential findings frozen at server start

`self.referential` is assigned only in `Store.load()`, called once from
`__init__`. `lint_debt()` caches correctly on `head_revn` but folds that frozen
set into every recompute, so a repair landing after server start can never
clear it. Measured: server said 2 errors, CLI said none, disk said none;
a restart dropped it to `1N`. The function's docstring states the principle it
breaks two lines above the break.

**Fix:** recompute `referential_findings` inside `lint_debt`'s cache-miss
branch, from the current scenes, keyed on the same `head_revn`. Keep the
load-time computation for the *pre-repair* report (that is `r4-7`'s fix and it
must not regress) — but stop letting it outlive its revision.

**Controls:** dangle a reference → both server and CLI report it; repair it in
a commit → both stop reporting it **without a restart**; and the load-time
pre-repair report still fires on a fresh load of a damaged project (fixture
replay).

### r5-2 / r5-3 — the round derived from queue depth

`effective_round = committed + (1 if queued)`. Apply drains the queue, the `+1`
evaporates because the commit auto-bump cannot fire when the base author is
also `agent`, and the header falls from `Round 3+` to `Round 2` while every
open pin's age drops with it. And the derived `+1` is *why* the agent omits
`set_round` on a chat-only turn — `status` already showed the advance.

**Fix:** on apply-from-pending, commit the round forward (carry the derived
value into the commit) rather than letting it evaporate. Keep the discard
behaviour as-is: discarding *should* reverse it.

**Controls:** queue → Apply → round is `N+1` and no pin age decreases; queue →
Discard → round returns to `N` (the documented reversal); and a chat-only turn
with an explicit `set_round` still lands as exactly `N` (the beats-B
anti-stacking fix must not regress — it is currently intact and this change is
adjacent to it).

**Doc half (r5-3):** the round doctrine must tell the agent not to read
`ROUND` as evidence its round advanced while anything is queued. See WP6.

## WP3 — The feedback surface under `pulled` (r5-6) + the cadence blind spot

Under `pulled` the apply response is `QUEUED=true / PENDING_ID / PIN_DEBT` and
**nothing else** — no `ECHO=`, no lint, no `CONSEQUENCE=`. v0.8's beat-3 fix is
unreachable on that path by construction, and the agent narrates its round
blind. Under `per-round` the identical batch returns the full echo.

**Fix:** compute echo and lint from the **staged** scene at queue time and
return them with `QUEUED=true`. The information already exists — the ops are
fully validated at queue time (an invalid batch is rejected, not queued) — it
is simply withheld. Mark the lines as provisional (`ECHO(queued)=`) so nobody
reads them as committed.

**Cadence blind spot (recorded in R5 §7, not separately filed):** `status`
prints twenty lines and none is the cadence; `canvas_updates` is read only
inside the apply path. Add `CADENCE=per-round|pulled` to `status` and to the
`start` banner. This is one line and it removes the only route by which an
agent can be surprised by queueing.

**Controls:** same batch under both cadences returns the same echo and lint
content (differing only in the `QUEUED`/`REVN` framing); and a *rejected* batch
under `pulled` still returns errors and no echo.

- **The endpoint lint is shape-blind, and it is silent exactly where the
  defect is worst** *(found by the Aug 2026 literature scan, then verified
  in-repo and measured here — not a run-5 finding)*. `lint_layout`
  (`canvas.py:5028-5094`) computes `outside`, `inside` and `run` against
  `tgt["x"/"y"/"width"/"height"]` — **the bounding box, with no `type` check
  anywhere in the block**. A diamond fills half its bounding box, so the four
  corners are empty canvas that the lint treats as node interior.

  Measured on a 200×100 diamond, arrow approaching horizontally, `TOL = 14`
  (`canvas.py:5001`):

  | endpoint | true visible gap to the rhombus | lint |
  |---|---|---|
  | (310,305) | **80px of white space** | **silent** |
  | (315,308) | 69px | **silent** |
  | (320,310) | 60px | **silent** |
  | (312,312) | 64px | **silent** |
  | (318,318) | 46px | fires |
  | (330,320) | 30px | fires |

  **The check is anti-correlated with severity in the corner region:** the
  nearer the endpoint drifts to the bbox corner the larger the real gap grows
  and the quieter the lint gets, because `inside` is measured to the *box*
  faces. That is the identical inversion the comment at `canvas.py:5031-5038`
  records having already fixed once for the far-edge case ("deeper penetration
  produced LESS warning — the opposite of a tolerance"). It was fixed for
  rectangles and never for shapes.

  And when it does fire the message is wrong: it says the endpoint "ends 15px
  **inside** the shape" for a point sitting in empty canvas *outside* the
  rhombus, so the repair advice points the wrong way.

  **The mirror defect, same root cause.** `_seg_hits_rect` (`canvas.py:4839`)
  is bounding-box by construction — its own docstring says so. Since the bbox
  strictly contains the shape, the crosses-through lint **over-fires** on edges
  threading a diamond's empty corner, where the picture reads fine. Fixing that
  direction can only ever *remove* findings, so it cannot introduce a miss.

  the node's *actual* outline (Cyrus–Beck for the rhombus, closed-form conic
  for the ellipse, existing bbox path for rectangles; ~40 lines, stdlib, and
  the repo already carries a Liang–Barsky-style parametric clip inline at
  `canvas.py:5043-5078` — same shape of code, four planes instead of two).
  Report the distance **signed**, so "floats clear in white space" and "buried
  inside an opaque shape" stop being one number. Normalise the threshold by the
  node's own scale rather than a flat 14px, which is 20% of a 60px pill and 5%
  of a 240px diamond. Then apply the same predicate at `_seg_hits_rect`.

  **Why this is near the front of WP4:** it is a *shipped* check reporting
  clean on the exact defect the whole geometry investigation was opened to
  catch, and headless agents — who cannot see their own drawing — are
  instructed to trust it. Also note it is the same failure family as `r5-14`
  and the curved-elbow item below: **the computed thing and the drawn thing are
  different objects.** Third instance found; treat that as the theme of this
  package, not a coincidence.

  **Control (both directions, per the standard):** the floating-corner endpoint
  above must fire *with a gap figure matching the rendered white space*, and a
  legitimately-attached diamond endpoint — plus the fanned attach points that
  caused the r4-1 over-fire — must stay silent. Gate on a render, since the
  client re-derives bound endpoints from `focus`/`gap` at draw time and stored
  points can disagree with what is drawn in **both** directions.

  **AXIS CONVENTION (binds the fix):** `endpoint_gap` magnitude is the gap
  along the arrow's **approach axis**, not the perpendicular distance to the
  facet — the catalogue mutants encode **80.0 / 50.0** (approach-axis), and a
  fix reporting perpendicular distance (**35.8 / 22.4**) will **not** flip
  them. Pick the other convention only deliberately, and re-magnitude
  `diamond_corner_silence` and `diamond_wrong_direction` in the same change.

  **The three mutants that flip here:** `diamond_corner_silence` (silent at
  80px), `diamond_wrong_direction` (fires "15px inside" for a point 50px
  outside), `diamond_facet_overfire` (errors on a perfect facet-midpoint
  attachment). The mirror bbox defect adds `foreign_diamond_corner_overfire`
  and `float_diamond_center_zero`.

- **Straight first, flare last — the geometry campaign's ordering**
  *(directed by the user; no measurement yet)*. Build the layout/routing
  workflow on **sharp** arrows, drive collisions and sloppiness down with
  adjustment passes until the plot is clean, and only then re-introduce
  curvature as a final aesthetic pass — applied gently on an **unsaved**
  candidate, re-checked after each increment, and **reverted to the last clean
  state at the first violation**.

  One line is the switch, `canvas.py:2024`: `arrow["roundness"] = None if
  len(pts) == 2 else {"type": 2}` — every straight arrow renders sharp and
  **every elbowed arrow renders curved**. In the r5 fixture that is 31 sharp and
  18 curved, i.e. every arrow that turns a corner.

  **Why the ordering is right, not just simpler.** Roundness here is *derived*,
  never authored — it is a pure function of the routed polyline, recomputed at
  load by `rebuild_bound_elements`. So going sharp discards no user intent and
  is reversible at any time; curvature is not a property we would be deleting,
  it is a pass we would be deferring. And while arrows are sharp, **stored
  geometry and drawn geometry are the same object** — which means every cheap
  check we already own (crosses-through, endpoint penetration, `floatdia`,
  `falsebidi`, `corridor`) measures the thing the user actually sees. That is
  the `r5-14` defect class collapsed at the source rather than patched: the
  round's headline geometry bug exists *because* the drawn line had drifted off
  the computed line.

  The case against curving them, all of it from this round's evidence:

  1. **The drawn line stops being the computed line.** The router and the
     crosses-through lint both reason in orthogonal segments; a rendered curve
     bulges off those segments, so a path the lint certifies as clear can render
     clipping a corner it never passed through. Same family as `r5-14`.
  2. **Endpoint ambiguity is the most repeated complaint in the round** — two
     cold looks and the spike all reported arrowheads that miss, float, or merge
     — and curvature degrades exactly that judgement, making a near-miss read
     worse and a hit read like a near-miss.
  3. **It compounds `r5-14`:** the erased corner leaves two truncated *arcs*
     pointing nowhere, where two sharp stubs at a right angle are completed by
     the eye. That is literally why a cold observer called a correct self-loop
     "a stray L-shaped stub".
  4. Minor: the mixed idiom makes a straight and an elbowed arrow read as two
     different *kinds* of relationship, which the tool does not intend.

  **Stage 1 — go sharp, and baseline.** Not a blind flip: produce a de-curved
  copy of the r5 fixture (`roundness: None` on the 18 elbowed arrows — no code
  change needed to test), render both at tier 1, and run `floatdia.py` and
  `falsebidi.py` (`~/docs/optimization/r5/mermaid-spike/`, see its README) over
  each. This is now a **baseline**, not a referendum — the numbers say how much
  of the endpoint ambiguity was curvature and how much is the router's, which
  tells stage 2 where to aim. Record them either way, so nobody re-litigates
  this from taste in a later round.

  **Stage 2 — make the plot clean with adjustment passes.** This is the rest of
  WP4's router work (`r5-5`, `r5-14`'s label placement, the endpoint checks),
  and it gets easier in exactly the way the user predicted: every pass can be
  scored by a cheap check over stored geometry, because stored *is* drawn. Ship
  the campaign here. The plot must be clean sharp before anything is added back.

  **Stage 3 — re-introduce flare under a violation gate.** Shape: propose a
  curvature increment on an in-memory candidate, re-run the geometry checks,
  accept if clean, and revert to the last clean state at the first violation —
  a hill-climb with a validity gate, never persisted mid-search. Two rules it
  must obey, both learned this round:

  - **The gate must measure the curve, not the polyline.** Re-adding curvature
    re-opens the drawn-vs-computed divergence, so a gate that reads the
    orthogonal segments certifies a picture it cannot see. The cheap way to keep
    the existing checks valid is to **flatten the rendered curve into a dense
    polyline and run them on that** — sampled from the same curve the renderer
    draws, verified once against a rendered pixel check to prove the flattening
    matches. That flattening is worth building for its own sake: it is the
    general fix for "the lint certified geometry nobody sees".
  - **Per-arrow, not global.** The gate will reject some arrows and accept
    others, which means roundness stops being a function of point-count alone
    and becomes a routing result. Keep it derived (so it never becomes a second
    source of truth), but derive it from the *checked* path.

  **Cost:** re-baselines every visual e2e snapshot, and changes the derived
  `roundness` on every existing artifact. `rebuild_bound_elements` already
  derives roundness at load (the v0.8 WP2 fix), so the change should propagate
  consistently rather than minting reconciliations — verify that on the fixtures
  before believing it, since `r5-13` is precisely a load-time repair that moves
  geometry and mints a commit every time.

- **Fix the scoring instrument before running either experiment** *(literature
  scan, Aug 2026; both bugs reproduced here)*. The sharp-vs-curved baseline and
  WP5's ELK comparison are both scored by `analyze.py`, and it cannot do the
  job:

  1. **`EDGE_CROSSINGS` counts crossing *pairs*, not crossings.** A `break`
     cascade exits both segment loops on the first hit per pair. Fed two arrows
     that genuinely cross **three** times, it reports `EDGE_CROSSINGS=1`. A
     router change that turns one crossing into three registers as no change.
  2. **It is blind to the exact defect `corridor.py` exists to catch.** `inter()`
     is a strict proper intersection — collinear overlap and shared endpoints
     both return `False`. Two arrows drawn along the same line with **300px of
     shared extent**, the worst reading failure the tool can produce, score
     `EDGE_CROSSINGS=0`, `ARROW_THROUGH_FOREIGN_NODE=0`, `LABEL_OVERLAPS=0` — a
     clean bill of health on every metric. Mooney et al. solve this inside the
     metric with a 2.5° angular tolerance below which a crossing is not counted,
     rather than in a second script.
  3. **Nothing is normalised**, so a 12-node seed and a 30-node hand layout are
     not comparable — which is the campaign's entire purpose.

  **What the evidence says to measure instead, and it is not what we chose.**
  For hand-laid *orthogonal* diagrams specifically (Kieffer et al., HOLA, TVCG
  2016 — the closest study to our regime), **compactness** correlates with human
  preference on **8 of 8** graphs, every one at p<0.01, r = 0.687–0.870 —
  stronger than crossings on every single graph — and **alignment
  ("gridiness")** is second at 8 of 8. `analyze.py` computes compactness,
  calls it `density`, and buries it on the last line; alignment is absent
  entirely. Bends are computed into a local variable and never printed.
  Meanwhile **angular resolution is an anti-metric for us**: HOLA scores badly
  on it *because* edges leave nodes orthogonally, so optimising it would
  penalise exactly the drawings we want.

  Alignment is also the metric most likely to expose the dagre gap, and for the
  reason we already diagnosed: dagre aligns within layers but not across them,
  which is the root cause of the floating-diamond endpoint.

  **Measured on our own corpus before adopting any of it (n=2, the spike's two
  head-to-head pairs):**

  | layout | compactness | gridiness | bends mean |
  |---|---|---|---|
  | 12-node seed (plain) | 0.2645 | 50.0% | 0.29 |
  | 12-node seed (best recipe) | 0.1417 | 58.3% | 0.36 |
  | 12-node hand | **0.1069** | **91.7%** | **0.14** |
  | 8-node seed | 0.2751 | 37.5% | 0.50 |
  | 8-node hand | **0.1155** | **75.0%** | **0.12** |

  **Gridiness works exactly as advertised** — hand-laid is ~2× more aligned in
  both pairs — and **bends agree**. Both track the qualitative verdict, and
  gridiness is the metric currently absent from our instrument. The authoring
  recipe measurably moves the seed toward the hand layout on both axes, which
  corroborates the spike's recommendation with a number rather than an eyeball.

  **But compactness picks the seed in both pairs, by ~2.5×** — including the
  8-node seed that drew a relationship which does not exist in the source. So
  the literature's single strongest-evidenced predictor of human preference is
  **anti-correlated with our own judgement on our own corpus.**

  The likely mechanism, and it matters: compactness rewards density, and our
  worst defect classes — shared corridors, false bidirectional junctions,
  floating endpoints in bbox corners — are all *caused by* density. Kieffer et
  al. ranked drawings that presumably did not contain them.

  **Consequence for the campaign: do not make compactness the headline.** Score
  layout quality on gridiness and bends; treat compactness as meaningful only
  *among drawings that already pass the defect gates* — the same "hard gate,
  then score" pattern the literature recommends for node overlap. This is
  exactly the internally-hostile metric vector the survey warns about, so
  report the vector and never paper over it with a single sum.

  *Caveats, stated because n is small:* two pairs, one diagram family, one tool;
  gridiness implemented from Kieffer et al.'s prose description (centre-based,
  6px tolerance), not their code. Enough to stop us leading with compactness;
  not enough to discard it.

  **Fix:** normalise everything to [0,1] with 1 = good; add bends (mean and
  max, not zero-targeted — the best human layouts contain deliberate aesthetic
  bends), alignment, node–node overlap and flow-direction consistency; promote
  compactness to the headline; demote raw area, raw ink and total edge length
  to diagnostics; keep the enumerated defect list, which is the one thing the
  script already gets right. Add **crossing angle** — near-constant at 1.0 on
  orthogonal baselines and therefore the metric that will actually detect a
  curved-elbow regression, which is what the stage-1 baseline above is for.
  Score consistency against whichever axis dominates, never a hardcoded
  left-to-right preference (Figl & Strembeck found no comprehension advantage
  for any direction).

  **How to declare a winner:** report the full normalised vector side by side,
  then a **win/loss/tie count** *and* a weighted sum with the weights written
  down, and call it a win only when the two agree. A single number hiding a 3–4
  split is the practice the evaluation survey exists to criticise.

- **Edge nudging — the fixer behind `corridor.py`** *(literature scan; the
  round's biggest direct transfer. **Scope decision: this is 250–350 lines and
  may belong in v0.10 rather than v0.9** — flagging rather than assuming.)*
  Our shared-corridor defect has a name — **edge nudging** — and it is solved
  three times over. The canonical academic treatment (Wybrow/Marriott/Stuckey,
  GD 2009) needs a constrained-optimisation solver we cannot take, but
  **Graphviz's `lib/ortho` implements the same pipeline with no solver at
  all**: drop each segment into its channel, compare pairs with a `seg_cmp`
  that decides "must be left of" purely from the two segments' extents and
  their bend directions at each end, topologically sort that into track
  numbers, and convert track to coordinate with an even spread
  `k/(n+1)`. `O(k²)` per channel with k typically 2–4 — free at our scale.

  This is precisely the "adjustment method" the straight-first ordering above
  calls for, which is why it lands in WP4 rather than in a router rewrite.

  Take libavoid's four production details, which are what a decade of shipping
  added to the paper: transitive region grouping computed by restart; a
  deferral-tolerant insertion sort, because the order is *partial* and a naive
  sort loops or crashes on incomparable segments; the
  reduce-separation-and-retry loop (ten attempts, then report unfixable as a
  lint finding rather than forcing a bad drawing); and **segments with a node
  endpoint are immovable by default** — non-negotiable for us given we already
  have a floating-endpoint defect. Plus Hegemann & Wolff's structure: two
  independent 1-D passes, never 2-D, and zero separation between segments of
  the *same* arrow.

  **Two cheap wins available immediately, independent of the fixer.** Split
  `corridor.py` findings by whether the two arrows share a bound element: a
  shared endpoint is a fanning artefact, no shared endpoint is the real "two
  relationships drawn as one line" defect (Luo et al.'s ambiguity-free
  bundling criterion, read backwards). And test Esri's "similar in length"
  filter — a 60px segment overlapping a 600px one is a tick on a long line, not
  a merged stroke — though do not adopt it blind.

  **Negative result worth recording so it is not re-searched:** the literature
  *prevents* this defect at routing time and essentially never detects it
  post-hoc. `corridor.py` is already at parity with the only shipped product
  that does post-hoc detection (ArcGIS Pro's *Partial Overlapping Edges*) and
  ahead of anything academic. **Do not invest in a better detector — the value
  is entirely on the fixing side.**

- **Render verification — the mechanism behind the new definition of done**
  *(literature scan)*. Three parts, in priority order.

  **1. Ablation delta (harness).** Render the real SVG, render it again with the
  element under test set to `visibility:hidden` — a change that removes ink and
  triggers no reflow — and diff. Three assertions, none needing a baseline:
  *existence* (`|delta| > 0`, or the element contributes nothing to the
  picture); *coverage* (`1 − |delta|/|solo_ink|` is the element's **occlusion
  fraction**, a reportable number); and *continuity* (**a connector's delta must
  be one connected component** — two means it is visually severed). The cheapest
  useful instance is two renders total: full, and full with *all* label
  backdrops hidden. Every connector pixel appearing only in the second image is
  label-occluded — **that single test would have caught `r5-14`.** Batch the
  per-connector version by toggling visibility inside one Playwright page, not
  by spawning a process per element.

  **Built, and here is what it learned** *(mutation harness,
  `tests/test_mutants_render.py`, behind `MUTANTS_RENDER=1`)*. Ablation
  existence and continuity both exist and both catch their class:
  `test_mutant_label_backdrop_severs_connector` passes today, which means
  **tier 1 already reproduces the opaque label backdrop** and r5-14's class is
  now measured from pixels. Two constraints came out of building it:

  - **Tier-1 `render_svg` ignores `opacity`:** a tier-1 ablation existence
    check cannot see a 0%-opacity ghost — an element invisible on the canvas
    is still ink in the export, so ablating it changes pixels and the check
    reports it present. Pinned as `expectedFailure` in
    `tests/test_mutants_render.py`
    (`test_mutant_opacity_ghost_is_invisible_to_tier_one`); **flips when
    ablation runs against tier 2.** Until then, the existence check's
    guarantee is "not in the export", not "not in the picture".
  - **`ablation_continuity` fires on any backdrop mid-stroke**, including the
    label-on-edge idiom on a straight run. The perceptual rationale says an
    occupied straight-run gap is **legitimate** — continuation completes the
    stroke through the label box — while an **erased corner is not**, because
    there is no collinear continuation to complete. The check may need exactly
    that exemption. The catalogue pins only corner-vs-beside today, so a fix
    that adds the straight-run exemption will not be caught by a mutant
    either way — write the mid-run-label mutant as part of that change.

  **2. Occupancy bitmap (`canvas.py`, stdlib).** Kittivorawong et al.'s
  bit-packed rasterisation: rasterise each mark into a screen-resolution bitset
  — a Python `int` gives bit-parallel row AND/OR for free — and overlap becomes
  a bitwise AND. Exact for arbitrary shapes, unlike bounding-box tests, which is
  the same lesson as the shape-blind lint above. Rasterise **the opaque label
  backdrop as the filled rect it actually is**, and the occlusion check moves
  from "the test suite catches it later" to "the generator refuses to emit it".
  It validates our model of the ink rather than the render, so it complements
  (1) and cannot replace it.

  **3. The comparator: one-pixel-tolerant XOR, not a perceptual metric.**
  Binarise to ink/paper, dilate each mask by one pixel, take
  `(A ∧ ¬dilate(B)) ∨ (B ∧ ¬dilate(A))`, run connected components, fail on any
  blob ≥ ~12px. **Anti-aliasing dies here by construction:** every AA, hinting
  and sub-pixel artefact is a sub-pixel edge displacement, i.e. at most a
  one-pixel band hugging a stroke, which the dilation absorbs — while a missing
  arrowhead is a free-standing blob that survives. The separation is sharp
  because the two differ in **topology, not magnitude**, which is exactly what a
  percentage threshold cannot exploit. ~120 lines of stdlib, and it reports
  bounding boxes, which is what makes a failing visual test fixable.

  **Explicitly rejected, with reasons, so they are not revisited:** SSIM — a
  diagram is ~95% flat paper, so a *fully erased connector* still scores ~0.997
  globally, while AA perturbs variance along every stroke; wrong sensitivity in
  both directions. LPIPS/FLIP — trained on photographs, out of distribution on
  line art, and unexplainable when they fail. Perceptual hashes — built to be
  invariant to small changes, which is the whole thing we are detecting.

  **The negative result on round-trip verification, and its reason.** Rendering
  the diagram and recovering the graph a viewer would perceive is *not* an
  established technique, and current accuracy (relation F1 ~0.91–0.98 for
  flowchart→Mermaid as of Dec 2025) is not why we should skip it. The reason is
  **bias direction**: a recogniser is trained to output the graph a picture like
  this most plausibly encodes, so when a connector's corner is erased by a label
  backdrop it sees two stubs, infers the join, and reports the edge present — and
  it does this *more* reliably the better it gets. The false-negative rate rises
  with model quality, on precisely our worst defect class. A perfect round-trip
  match tells us only that the picture is legible enough to guess from.

  **Determinism first — this is where most of the win is** (and it gates WP8's
  visual snapshots): pin Playwright's bundled Chromium rather than
  `/snap/bin/chromium`; embed the font as a base64 `data:` URI in the SVG;
  add `--force-color-profile=srgb`, `--font-render-hinting=none`,
  `--disable-font-subpixel-positioning`, `--disable-lcd-text` to the three flags
  `fullshot.py` already sets; and **pin the Excalidraw `seed` on every element in
  every fixture** — roughjs derives its hand-drawn stroke jitter from it, so
  unpinned seeds mean *every stroke differs on every run* and no comparator can
  save us. If a test still flakes after that, the diagram content is
  non-deterministic and that is the bug. Never raise the blob threshold to
  silence a flake.

  **Tier the gate so it does not rot:** Tier 1 is the invariants above — no
  baseline, never stale, and where the real defects live. Tier 2 is a
  deliberately small set of 8–15 golden images. The long-term killer of visual
  suites is documented: baselines rot, engineers rubber-stamp diffs, the suite
  becomes ceremony. Keep the golden set small and derive most assertions from
  invariants.

  **Two `fullshot.py` notes:** its `width='(\d+)'` regex matches our own export
  today (`canvas.py:4543` emits `width='%d'` in single quotes), so that is latent
  fragility rather than a live bug — but it constrains only *height*, so a very
  wide drawing can still overflow the window and crop, which is the exact failure
  the script exists to prevent.

  **One free UX idea worth taking:** our output format is already sketchy, so a
  lint failure can emit a layer of red Excalidraw annotations pointing at the
  occluded connector *in the same file* — the human sees it the moment they open
  the canvas, instead of a diff PNG in a CI bucket.

## WP4b — Faithfulness: the drawing must not assert what the model does not say — **CANDIDATE, scope decision needed**

*Entirely from the Aug 2026 literature scan. Not committed to v0.9 — see the
scope note at the end of this package.*

**The literature gave this class a name and a warrant.** Nguyen & Eades'
**faithfulness** (PacificVis 2013) is the argument that readability criteria —
few crossings, few bends, small area — are *necessary but not sufficient*: a
drawing can be maximally readable and still lie. Their worked example is a
confluent drawing in which "one may see a curve connecting the two red circles"
that does not exist in the source. **That is `r5-11` structurally** — the seed
that drew a relationship absent from the source while lint reported
`FINDINGS=0`. This is the citation to put in `AGENTS.md` behind the claim that
lint-clean ≠ correct, and it gives the linter a clean seam: **readability
findings vs faithfulness findings.**

**We are at the frontier here, not behind it.** The 2023 Dagstuhl seminar on
perception in network visualization named this exact agenda — *"unintended
perceptual inferences"* — and it has produced **no follow-up publications and no
code**. No linter for node-link false readings exists; VisuaLint, VizLinter and
the misleading-chart work are all chart-grammar-level (axes, scales) and none
looks at drawn geometry. Orthogonal routing in particular is *perceptually
under-studied* — the empirical literature is overwhelmingly straight-line and
force-directed, so several of our defect classes are absent from it entirely.

### The unification, which is a refactor rather than new research

The one framework worth adopting is the **proxy graph / shape-based metric**
(Eades, Hong, Nguyen, Klein, JGAA 2017): build **P**, the graph a viewer would
perceive, and diff it against **G**, the source, as precision/recall. Every
existing instantiation builds P from **node positions only**, because it targets
force-directed drawings of thousands of nodes. **Nobody builds P from rendered
stroke geometry** — that gap is exactly where our scripts already sit.

And our scripts are already partial P-builders:

- `falsebidi` → an edge in **P** that is not in **G** (`phantom_edge`)
- `floatdia` → an edge in **G** not reliably in **P** (`weak_edge`)
- `corridor` → several edges in **G** collapsing to one in **P** (`merged_edge`)

Unify them behind one `perceived_graph()` returning a typed diff, and the
defect classes below become *cases of one function* instead of seven more
scripts. Fully stdlib — sets, tuples, `math`.

Second shared primitive: **good continuation**, one helper answering "are these
two segments perceptually one stroke?", parameterised by collinearity
tolerance, gap and turn angle. Ware et al. (2002) supply both the empirical
backing — continuity is, after path length, among the strongest predictors of
path-tracing difficulty — and the tolerance: V1 orientation tuning is coarse,
roughly ±30°. Note their prediction that **orthogonal layouts read *worse* than
curved ones**, because every segment is one of two orientations, so
"accidentally collinear" is the normal case for us and not the exception.
Continuation defects are structurally *more* likely in our output.

### Defect classes we have never checked, ranked by expected hit rate

1. **Phantom pass-through (e1) — the highest-value item in the scan.** Arrow
   `X→N` arrives at N's left edge and `N→Z` leaves N's right edge, both
   horizontal at the same y. Good continuation reads them as **one stroke
   passing behind N**: the viewer infers a direct X→Z relation and demotes N to
   a label on the edge. In a flowchart that **silently deletes a step.** The
   inverse also bites — an edge genuinely passing behind a node reads as two
   edges terminating there. **Dagre produces this configuration constantly, by
   design**, because its whole job is putting chained nodes on one rank line.
   Test is O(deg²) per node: same orientation, supporting lines within
   tolerance, entering and leaving on opposite sides.

   **The harness already produces this survivor, so the flip signal is
   wired.** The first discovery sweep mints
   `move_node_onto_rank:chain:ebb2e1f6` — *"phantom pass-through at node N
   (e1 -> e2 collinear, unflagged)"* — dispositioned **promote** in
   `DISPOSITIONS` (`tests/test_mutants.py`), with this item cited as its
   reason. Landing the e1 lint will make
   `test_live_sweep_reproduces_the_record` **fail loudly**, because the live
   sweep will no longer produce the survivor that the committed
   `tests/mutants_sweep.json` records. That is the intended flip signal for a
   *discovery* finding — the counterpart of an unexpected success for a
   curated one. The response is not to suppress it: re-run
   `python3 tests/test_mutants.py --sweep`, re-commit
   `tests/mutants_sweep.json`, and retire the now-dead disposition, all in the
   same change as the lint.

   **The configuration is now pinned by a curated mutant too**, so the
   disposition above is executed rather than merely recorded:
   `phantom_passthrough_shared_attach` (`tests/test_mutants.py`) rebuilds the
   exact geometry the 2026-08-12 ELK spike shipped — both edges on one attach
   point on N, drawn as one unbroken 448px horizontal stroke through the box —
   and asserts `FindingSpec("phantom_passthrough", element="N")`. It is red
   **by absence**: there is deliberately no `phantom_passthrough` entry in
   `DETECTORS`, so it fails with *"no finding of check='phantom_passthrough'"*
   until this lint exists. Flip it by adding that entry and dropping the
   `@unittest.expectedFailure`. Two green mutants on the same scene fix what
   the current tooling does and does not see: `merged_stroke_caught_by_corridor`
   (corridor.py's abutting-run case is the net that catches a full-run merge;
   `falsebidi` scored the production case 0, final-segment-only) and
   `shared_attach_point_fan_failed` (our own lint names the node and says the
   auto-fan left them together).
2. **`falsebidi.py` is itself measuring the path, not the picture (e7)** — a
   correctness bug in the script, not merely a missing rule. `final()` takes
   `points[-2] → points[-1]`, the stored chord, while Excalidraw's `roundness`
   curves the corner, so the **rendered tangent at the tip differs from the
   direction the script computes**. In `tests/fixtures/argus-r5` that is
   **18 of 49 arrows (37%)**. A curved elbow can therefore both hide a real
   false-bidi and manufacture a spurious one. Same root cause as the curved-elbow
   item in WP4, and the same error the round already recorded once —
   [[assess-the-picture-not-the-path]].
3. **Ambiguous endpoint (e3)** — a strictly better framing than `floatdia.py`'s
   absolute distance, and it subsumes it. The question is not "how far from its
   own node" but "**is it unambiguously nearer its own node than any other?**"
   Flag when `d2 < k·d1` for k ≈ 1.5. One number, scale-free, no tolerance
   guessing. Borrowed from cartographic label placement; the transfer is ours,
   not the literature's.
4. **Arrowhead collision (e6) — the one item on this list with an experiment
   behind it.** Holten & van Wijk (CHI 2009) found arrowhead *overlap* is
   precisely why arrowheads underperform for direction tasks; tapered edges beat
   them on time and error. We cannot switch encodings — Excalidraw has no
   tapered primitive — so we are stuck with the empirically worse one and should
   lint it harder. Cite the study in the finding text.
5. **Crossing at a bend (e5)** — two orthogonal edges crossing exactly where one
   turns is locally identical to *two edges that each turn*, so the viewer may
   attach either incoming segment to either outgoing one and **two relations
   swap endpoints**. Specific to orthogonal routing, therefore specific to us,
   and structurally invisible to every straight-line metric in the literature.
6. **T-junction merge (e4)** — an endpoint or bend landing *on* another arrow's
   stroke reads as "these flows join". Corridor-sharing produces it routinely.
7. **Edge tunneling and near-miss grazing (e2)** — formalised and named by
   Dunne & Shneiderman; we check neither the through- nor the near- case. An
   edge clipping a corner by 3px looks *deliberate*.
8. **Total occlusion / degree undercount (e8)** — coincident edges, an edge
   hidden behind a node, an arrowhead entirely inside its target. Breaks
   "for every node you can count its degree". **The class most likely to be
   invisible in review, because nobody notices what isn't drawn.**
9. **False containment (e9)** and **label misattachment (e11)** — the latter
   shares e3's arithmetic, so it is nearly free once e3 exists.
10. **Degenerate arrow geometry (e15) — do this one first.** Near-zero final
    segment (so arrowhead direction is numerical noise), duplicate consecutive
    points, coincident endpoints, head overshooting the far border. Not
    perceptual, but these are the inputs that make every check above return
    garbage.

Deferred with reasons recorded: false cluster by proximity (e10 — weak signal on
deliberately laid-out grid diagrams), spurious alignment (e12 — would fire
constantly on grid-snapped output; only worth building with an NFA threshold),
motif similarity (e13 — the research is not in yet).

### Two method upgrades worth more than any single rule

- **Metamorphic fixtures find defect classes on purpose.** Kindlmann &
  Scheidegger's algebraic method, turned into a property test: mutate the source
  model (drop an edge, flip a direction, rename a node), re-render, assert the
  picture changed correspondingly. Anything that survives a source mutation
  **without** a picture change is a *confuser* — a place where the drawing
  cannot distinguish two different models. This is the direct answer to "we
  found `falsebidi` by accident and there are certainly siblings". Pure stdlib;
  the comparison is over our own JSON.
- **A-contrario thresholds are the honest answer to "why 8 pixels?"**
  `falsebidi.py` carries five hardcoded tolerances with no derivation and
  `corridor.py` two more. The Helmholtz principle asks instead: given this
  drawing's segment count, orientation histogram and extent, how many
  opposed-collinear-overlapping pairs would we expect **by chance**? Report a
  grouping only when the expected count is far below 1. Scale-free, adapts to
  density automatically, and collapses seven tuning constants into one ε.
  `math.lgamma` gives the binomial tails in a dozen lines. **Defer until the
  fixed tolerances actually misbehave** — but this is the reach-for when they do.

### Honesty note to carry into the code

**No study compares double-headed arrows against paired opposed single arrows.**
`falsebidi`'s premise is well-motivated by continuity theory and by Holten's
arrowhead-overlap result, but it is **not empirically established**. Say so in
the docstring rather than implying otherwise.

### Scope

This package is a **candidate, not a commitment**. Ten new lint rules plus a
`perceived_graph()` refactor is comfortably larger than the rest of v0.9. The
defensible minimum, if v0.9 takes only part of it: **e15 (degenerate geometry,
because everything else depends on well-formed input), e7 (a live bug in an
instrument we are about to rely on), and e1 (the highest hit rate, and dagre
manufactures it).** The rest can wait for v0.10 without losing anything — the
research is archived at `~/docs/optimization/v0.9-geometry-research/`.

## WP5 — Mermaid: fix the authoring guidance, keep the feature honest (r5-9, r5-10, r5-11 + spike)

**Superseded by the layout spike** (13 probe projects, scale sweep, two
head-to-heads, five layout knobs; full report in the session log). The A-vs-B
choice I posed is the wrong question — the spike found a **third and cheaper
answer**, and it also killed the doc claim outright.

### What the spike established

- **The "~7 nodes" claim fails.** At **8 nodes** — one above the stated
  threshold — the seed drew a **relationship that does not exist in the
  source** (two opposite-facing arrowheads 11–31px apart on one horizontal run,
  reading as `Order cancelled ⟷ Authorise payment`) and lint reported
  `FINDINGS=0`. The hand layout of the same graph was correct, also lint-clean,
  and cost under two minutes first-try.
- **Fidelity is flawless at every size** — 5/8/12/20/34 nodes, counts match the
  source exactly, labels byte-identical, shapes and reflexive edges correct,
  nothing dropped or invented. The *capture* is solid; the *layout* is what
  fails.
- **Wall clock is flat at ~10–11s regardless of size** (it is the headless
  browser launch). A real argument for the feature at 34 nodes, none at 5.
- **Three authoring knobs close most of the gap**, and they are free:

  ```
  %%{init: {'flowchart': {'nodeSpacing': 100, 'rankSpacing': 140}}}%%
  flowchart LR
    <happy path, every edge, start to finish>
    <then every exception / branch / back-edge>
  ```

  `LR` over `TD` is the biggest lever — it eliminates floating diamond
  endpoints (2→0) and turns a 3.5-screen scroll into a one-screen band.
  **Declaration order is the cheapest** — dagre's within-rank ordering follows
  it, and happy-path-first *removes the 8-node false-junction defect outright*.
  Together at 12 nodes: **0 lint findings, 0 crossings, 0 corridors, 0
  through-node arrows, 0 false junctions** — parity with the hand layout, not
  superiority.

## WP6 — SKILL.md: the event loop, said plainly

**Start from the measurement, not from an assumption.** Run 5 recovered the
burned r4-6 measurement and it is a **PASS, n=2**: both fresh agents, with no
hint from either user, found the doctrine, `ToolSearch`ed the deferred `Monitor`
schema, and armed it `persistent: true` with the mine-vs-yours filter — and
*extended* the shipped filter with the three types it omits. The doctrine is
being followed. The rewrite below is therefore **not** about emphasis; it is
about the four things the section does not say, each of which cost something
this round.

Replace the § *The event loop* body with the following (proposed text, for
review — the section keeps its position and heading):

> ## The event loop — watch the log, react to their moves
>
> **This is standing procedure, not a fallback. After every move of yours, arm
> a watch on the events log, and treat what lands as the user's move.** The log
> path is printed by `start` and `status` as `EVENTS_LOG=`; one JSON line per
> event.
>
> **Arm it like this** (`Monitor`, `persistent: true` — you are re-invoked per
> event and your turn still ends normally). Filter to the user's events or you
> will be woken by your own echoes; in a real session your own revisions were
> 87% of the traffic, and an unfiltered agent narrated its own drawing back as
> the user's move:
>
> ```
> tail -n 0 -F "$EVENTS_LOG" | grep -E --line-buffered \
>   '"type": ?"(save|pin_answer|tripwire_answer|checkout|checkout_live|branch_switch|branch_archive|suggest_view|config_changed|reconciliation)"'
> ```
>
> That list is **every** type that belongs to the user. Do not trim it: two
> independent agents had to add `checkout`, `checkout_live` and `branch_archive`
> back after copying an older, shorter version of this filter.
>
> **The event is not a notification — for some moves it is the only place the
> content exists.** `status` will tell you a pin is `answered`; it will never
> tell you *what the user answered*. That text is in the `pin_answer` event and
> in `/api/state`, nowhere else. The same is true of a `config_changed` patch.
> If you only ever poll `status`, canvas-first questions become a place where
> the user's answers go quiet.
>
> **Four things the log is the only witness to:**
>
> | You see | It means | Do this |
> |---|---|---|
> | `config_changed` with `canvas_updates` | the user changed the **cadence** mid-session | re-read `CADENCE=` in `status`; under `pulled` your next apply queues instead of landing, and the response will say `QUEUED=true` |
> | `reconciliation` | either a load-time repair or a real outside edit | read the record — it names which. After a restart, also check `PENDING=`: a queued revision does not survive a restart, and its loss is otherwise silent |
> | `checkout` / `checkout_live` | the user is looking at, or working from, an **older revision** | do not apply onto their head until they save; a save on top of a checkout forks a branch |
> | `save` with `forked: true` | they just forked | say so, and say what is stranded on the old branch |
>
> **Tier 3 — no `Monitor` tool?** `canvas.py wait --timeout 540` (defaults to
> `--for user`, same filter server-side; exits 3 on timeout, strictly under
> Bash's 600s ceiling). **Tier 2 — `AskUserQuestion`** is for before the canvas
> exists, or a question that genuinely cannot live on an element.
>
> **Re-arm after every move, and after any restart.** A watch does not survive
> the server going down, and neither does anything on the banner.
>
> **An arriving user event IS the user's move.** Read it, narrate it, act —
> do not wait for a chat message to confirm what the log already told you.
